## Контекст: что чинили (живой тест 31.07)

Репетитор — ноут/Chrome/WiFi; ученик — Android PWA/Мегафон, вошёл гостем по /b/-ссылке из чата.

1. **P0: репетитор пишет — у ученика НИЧЕГО даже через 20-30с.** Корень: watermark гостевого поллинга сверялся по ЧАСАМ — пустой тик двигал его на `now()` Deno-изолята, `updated_at` строк ставит Postgres (старт транзакции), а фолбэком были часы телефона. Skew часов ≥ интервала поллинга = гость слеп навсегда (каждый пустой тик снова уводит watermark в будущее); даже без skew транзакция, закоммитившаяся после запроса, проглатывалась.
2. **Ученик→репетитор 2-3с** при требовании ≤1с (дебаунс автосейва 900мс).
3. **У авторизованного ученика не было фолбэка вовсе**: `CHANNEL_ERROR`/`TIMED_OUT` молча глотались + гонка JWT (подписка ревс-канала без `setAuth` → join под anon → `REVOKE ALL` → тихий отказ).
4. **UX**: «раздать зоны» — серая ссылка на дне диалога (владелец не нашёл), а главная кнопка «Отправить ученикам в чат» не работала без розданных зон (порядок обратный).

## Архитектура после пасса (проверь, что код ей соответствует)

- **Rev-diff вместо часов**: `GET /share/:slug/signals` отдаёт ПОЛНЫЙ список ревизий доски (`page_id, rev, …`, ~2-3 КБ, ≤50 страниц); `since` игнорируется (обратная совместимость — старый бандл получает непустой revs и resync'ает каждый тик). Клиент (`SharedBoardView.handleRevsSnapshot`) сверяет rev с локальными кадрами; часов в контуре нет, пропуск самовосстанавливается. Троттлы `wb:sig`/`wb:state` 40→60/мин.
- **`boardSync.ts` (новый)** — транспорт авторизованных: машина `live | polling | offline`. WS SUBSCRIBED → страховочный полл 1/мин; WS не живой → PostgREST-полл `board_page_revs` 2с (RLS `board_page_revs_participant_select` уже разрешал — миграций нет); ≥2 сбоя полла → offline. Только chained `setTimeout` (PWA-фриз убивает interval); `visibilitychange`/`online` → немедленный тик + `realtime.setAuth()`; грейс 8с на бейдж «polling» (не флапать при старте).
- **Харднинг WS** (`boardRealtime.ts`): `setAuth()` ДО subscribe; `onStatus` наружу; телеметрия `reportClientError('board_revs_channel_*','net')`; `removeChannel` вместо `unsubscribe` (утечка каналов, оба модуля).
- **Латентность**: `BOARD_AUTOSAVE_DELAY_MS=300` + `maxWaitMs=1000` (непрерывное черкание не откладывает flush бесконечно — тест в autosaveQueue.test.ts); гость 2.5→1.5с активный / 15→10с hidden + немедленный тик на возврат видимости.
- **Фаза 2 «мгновенный контур»**: завершённый элемент (pointerup) → broadcast `element` по существующему private live-каналу (`sendElement`/`onElement`; 1 msg/штрих, кап 30 КБ, вход через `parseElements`); получатель мержит `reconcileElements` БЕЗ смены rev — БД-путь остаётся источником истины и догоняет rev-сигналом идемпотентно (LWW по version/versionNonce). Инвариант «ink не через Realtime» УТОЧНЁН: запрещён ПОТОК точек, single-shot коммиты разрешены (расчёт: ≤3 пишущих × 1-2 штриха/с ≪ 500 msg/s проекта). Гости не в канале — им поллинг 1.5с.
- **UX**: диалог «Пригласить» = два равноправных пути — primary «Отправить ученикам в чат» БЕЗ предусловий (доска занятия сама раздаёт листы участникам; без занятия открывает пикер «раздать и отправить»; шлёт АВТОРИЗОВАННУЮ ссылку `/student/board/:id` — читатель чата залогинен → WS+broadcast вместо гостевого поллинга) и secondary-кнопка «Раздать листы ученикам» (вместо серой ссылки). Панель «На доске»: muted-чипы офлайн-владельцев листов + постоянная кнопка «Раздать листы» + единый слот статуса (контентный sync приоритетнее live-курсоров). Пикер: «Выбрать всех», пометка «уже есть лист». Язык UI — «листы», не «зоны».

## Приёмочные сценарии (проверять КАЖДЫЙ по коду, таблицей ЗАКРЫТ/ЧАСТИЧНО/НЕТ)

1. **Гость никогда не слепнет**: при любом skew часов edge↔БД↔устройства и при транзакции, закоммитившейся после запроса `/signals`, изменение доезжает не позже следующего тика (в rev-diff нет пути потерять сигнал навсегда).
2. **Мёртвый WS у авторизованного** (ученик /student/board, репетитор): контент продолжает ехать поллингом ≤3.5с; индикатор «резервный режим» ≤10с; восстановление WS возвращает live без дублей применения.
3. **Холодный старт PWA**: подписка ревс-канала не уходит под anon (setAuth до subscribe); даже если WS так и не поднялся — поллинг активен с первой секунды.
4. **Разворот PWA из фона / `online`**: немедленный догон у гостя И у авторизованных (не ожидание хвоста hidden-таймера).
5. **Латентность**: авторизованный↔тьютор p50 ≤0.4с (broadcast-элемент); гость→тьютор ~1с (дебаунс 300 + POST + WS); тьютор→гость ≤2с (полл 1.5с). Непрерывное черкание — flush не позже 1с от первой грязи.
6. **Идемпотентность двух контуров**: broadcast-элемент, затем DB-refetch того же элемента (и обратный порядок, и приход во время 409-merge) — итог одинаков, rev управляется только БД, undo/протекшены выделения не ломаются.
7. **«Отправить ученикам в чат» без предусловий**: доска занятия → авто-раздача участникам → отправка; доска без занятия → пикер «Раздать и отправить (N)»; сбой раздачи НЕ отправляет ссылки. Ссылка в чате — авторизованная, и получатель после раздачи листа проходит `is_board_participant` (zone-ветка).
8. **«Раздать листы» находима**: две точки входа (диалог + панель), офлайн-владельцы видны в панели, гости/ученики не задублированы в чипах (CRM-гость офлайн не даёт двух чипов).
9. **Троттлы не душат сами себя**: гость 1.5с = 40 req/мин фактических при лимите 60; resync'и `/state` при активном уроке не упираются в 60/мин; порядок деплоя edge→фронт зафиксирован (старый фронт с новым edge и наоборот — оба живут).

## Что проверять сверх приёмки (по приоритету)

1. **Архитектура немедленности — есть ли дыра, где обновление всё ещё может «зависнуть навсегда»?** Прогони мысленно все пары (тьютор/ученик/гость × пишет/читает) × (WS жив/мёртв/флапает, вкладка фон/фронт, сеть рвётся посреди tick/resync). Особо: busy-флаг resync у гостя (сбой всегда снимает?); `ticking`-guard в boardSync (может ли цепочка тиков оборваться навсегда — например, исключение между `ticking=true` и `finally`?); rejoin-флапы WS не перезаводят таймер полла в бесконечность.
2. **Двойной контур (broadcast + БД)**: воскрешение стёртого ластиком элемента чужим поздним broadcast'ом? (reconcile без tombstones — известное ограничение, НЕ флагать как новое, но проверь, что Фаза 2 его не УСИЛИВАЕТ: broadcast шлётся только для НОВЫХ элементов, не для правок/undo); элемент в чужой/несуществующий лист; злонамеренный payload участника (parseElements достаточен? NaN/огромные points/битый seq); нагрузка при группе 8-15 одновременно пишущих (msg/s, ре-рендеры получателя на каждый элемент).
3. **Оптимальность горячих путей**: `handleRevsSnapshot` на каждый тик (find в цикле по кадрам — ок при ≤50, но не N²-взрыв?); полный список revs каждые 1.5-2с — байты/аллокации; ре-рендеры от `setSyncState`/бейджей (memo-цепочки не сломаны, полоса участников не дёргает BoardCanvas); `offlineSheetOwners`-memo deps.
4. **UX-критика как продакт**: интуитивен ли новый диалог «Пригласить» без обучения (иерархия двух путей, копирайт, порядок)? Панель: не переполнится ли полоса чипами на группе 15 (overflow-x — достаточно?); понятен ли «Раздать и отправить»; тексты индикаторов не пугают (rule 95 — сеть нейтрально). Сравни с ментальной моделью whiteboard.chat/Chattern.
5. **Регрессии прошлых закрытий**: CAS/base_rev (сейв-путь не тронут?); private-канал и его RLS (новый event `element` проходит те же политики `board_live_send/recv`?); fail-closed `/state`; гард выхода с flush; «watermark только после успешного resync» (ревью guest-sheets) — корректно ли ЗАМЕНЁН rev-diff'ом, а не потерян.
6. **Rule 80 (Safari 15/iOS 15)**: нет lookbehind/`Array.at`/`structuredClone`/`crypto.randomUUID`; таймеры/визибилити-паттерны; 16px. Rule 97 (non-2xx JSON RU) в правке edge. Rule 96 — клиент только `@/lib/supabaseClient`.

## Осознанные решения владельца (НЕ флагать как P0)

- Broadcast single-shot элементов по Realtime — санкционированное уточнение инварианта «ink не через Realtime» (поток точек по-прежнему запрещён).
- Авторизованная ссылка в чате вместо гостевой — намеренно (читатель чата залогинен); гостевая /b/ остаётся в поле копирования.
- Гость без live-канала (нет JWT) — его потолок = поллинг 1.5с, это принято.
- Bearer-модель гостя (Zoom-паттерн) — принята ранее, не пересматривать.
- `since` в `/signals` игнорируется молча (не 400) — намеренная совместимость деплой-окна.
