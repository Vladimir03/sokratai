# Работоспособный прод: метрики и план

**Дата:** 2026-07-26 · **Решения владельца:** свой пайплайн метрик → `/admin`; оба сегмента с разными порогами; порядок «довести до прода → измерить → перф»; unit-тесты начать с денег и грейдинга.

## Section 0: Job Context

**Core Job репетитора:** «вести больше учеников, не проверяя ДЗ ночами». **Core Job ученика:** «разобрать домашку самому и получить честную оценку».

Обе ломаются одинаково — не отсутствием функций, а тем, что продукт **не открылся или не ответил**. Белый экран на `/tutor/schedule` = репетитор не провёл занятие. Не догрузившийся чанк на `/student/homework/:id/problem` = ученик не сдал ДЗ, и ступень воронки 5→6 не случилась. Поэтому «качество кода» здесь не абстракция: оно измеряется тем, доходит ли пользователь до результата.

**Ключевая проблема на 2026-07-26: результат не измеряется.** В репозитории нет ни одной точки измерения скорости (`web-vitals`, `PerformanceObserver` — ноль вхождений). О поломках узнаём из скриншотов в Telegram: инцидент Глеба (Safari <16.4, lookbehind) нашли через дни, дрейф CHECK'а предметов — через два месяца и только по жалобе Ульяны. Пока нет измерений, любая оптимизация — угадывание, а Lighthouse тем более не покажет реальность: узкое место — РФ-DPI и кросс-граничный хоп до `api.sokratai.ru`, чего лаборатория не воспроизводит.

## 1. Метрики (главное)

Пороги CWV — по **p75**, **раздельно mobile/desktop**. INP заменил FID в 2024-м. Один общий числовой таргет врёт, поэтому цели разведены по сегментам.

### L0 — Надёжность: «продукт вообще работает»

| Метрика | Как считаем | Источник | Цель |
|---|---|---|---|
| **Crash-free sessions** | `1 − сессии с client_error / все сессии` | `analytics_events` (8 kinds) | ≥ 99.5% |
| **Белые экраны / 1000 сессий** | kinds `screen` + `chunk` + `window` | `analytics_events` | < 1 |
| **MTTD** — время до обнаружения | от первого события до реакции | вручную, по журналу | < 1 ч (сейчас: **дни**) |
| **Успешность AI-проверки ДЗ** | `1 − ai_gateway_errors / попыток` | `ai_gateway_errors` + `token_usage_logs` | ≥ 99% |
| **Retention ассетов** | прошлый entry = 200 после деплоя | шаг 9 `deploy.sh` (само-верификация) | 100% деплоев |
| **Edge error rate** | non-2xx по функции | логи + `client_error` kind `net` | < 0.5% |

### L1 — Скорость: field-метрики, не лаборатория

| Метрика | Ученик (mobile, старые iPhone, мобильный интернет) | Репетитор (desktop) |
|---|---|---|
| **LCP** p75 | ≤ 2.5 с | ≤ 2.0 с |
| **INP** p75 | ≤ 200 мс | ≤ 200 мс |
| **CLS** p75 | ≤ 0.1 | ≤ 0.1 |
| **TTFB** p75 | ≤ 1.2 с | ≤ 0.8 с |
| **API p95** к `api.sokratai.ru` | ≤ 2.0 с | ≤ 1.5 с |

**Route-level** (4 экрана, где живёт ценность):
- ученик — `/student/homework/:hwId/problem/:taskId` (главный рабочий экран),
- ученик — `/chat`,
- репетитор — `/tutor/homework/create` (самый тяжёлый: конструктор),
- репетитор — `/tutor/home`.

**Замеренный старт (2026-07-26, без gzip):** критический путь **696 КБ** (entry 180 + react-vendor 160 + supabase 129 + ui-components 99 + CSS 214). Экран задачи ученика догружает katex 259 КБ (статически в **35** чанках) + сам экран 95 КБ ⇒ **≈1.14 МБ до первого действия**. Это «до», от которого считаем эффект.

### L2 — Продуктовый результат (уже считается в «Пульсе»)

| Метрика | Смысл |
|---|---|
| **Конверсия ступени 5→6** | ученик открыл ДЗ → сдал. Прямое «продукт сработал» |
| **NSM: Weekly Value Tutors** | репетиторы, чей ученик сдал ДЗ за 7 дней |
| **% ДЗ с вердиктом AI без ручного вмешательства** | автоматизация реально экономит вечер |
| **At-risk репетиторы** | платит/триал и нет сдач 7 дней |

Связка с L0/L1 — то, ради чего всё: падение crash-free или рост LCP должно быть видно как просадка 5→6.

### L3 — Код и процесс

| Метрика | Сейчас | Цель |
|---|---|---|
| Lint errors | 201 (было 714 — две трети было шумом worktrees) | ≤ 50, и **0 в `src/`** |
| Unit-тесты money+grading | **0 (раннера нет)** | ledger, `computeFinalScore`, чекер Ч1, квоты |
| Smoke-check секции | 21 | растёт вместе с инвариантами |
| Always-loaded контекст агента | 28 345 токенов (было 163 414) | ≤ 30 000 |
| Deploy success / rollbacks | не считается | 100% / 0 |

## 2. План работ

### Этап 1 — ДОВЕСТИ ДО ПРОДА ⚠️ блокер

Фикс белых экранов **сейчас не активен**: код в `main`, но стаб деплоя не установлен на VPS, а фронт с фиксами ревью не задеплоен. До этого шага все остальные метрики бессмысленны — мы измеряли бы состояние, которое собираемся менять.

1. Установить `deploy-sokratai.stub.sh` на VPS, задеплоить **дважды**, приёмка: `curl -sI https://sokratai.ru/assets/index-<хэш-из-первого-деплоя>.js` → **200** (сегодня 404).
2. Задеплоить фронт (фиксы ревью: chunkReload, ErrorBoundary, streamChat, SW, retry-капы).
3. P0 из ревью — история публичного CSV: решение владельца (`git filter-repo` + force-push + форки + кеши GitHub).
4. Удалить 18 ветвей с публичным `.env` (значения `VITE_*` публичны по построению, ротировать нечего — но ветки создают ложный сигнал при каждом аудите).

### Этап 2 — ИЗМЕРИМОСТЬ

5. `web-vitals` (~2 КБ) → новая edge `web-vitals-report` → `analytics_events`. **Своя функция, не `client-error-report`**: у той глобальный кап 120/мин, для CWV этого мало. Нужны сэмплирование и отдельный кап.
6. Вкладка **«Скорость»** в `/admin`: p75 по роуту × роли × устройству, тренд по дням, МСК-бакеты (rule 101).
7. Health-check + алерт: сейчас мониторинга **нет вообще**, единственная проверка — `curl` в конце деплоя.
8. **Baseline-замер:** зафиксировать L0/L1 до оптимизаций. Без этой точки эффект недоказуем.

### Этап 3 — ПЕРФ (по цифрам; две позиции точны заранее)

9. **katex лениво** — 259 КБ статически в 35 чанках, при том что `MathTextInner` имеет документированный zero-KaTeX путь для текста без `$`. Не трогать `manualChunks` (`vite.config.ts` фиксирует измеренную регрессию +265 КБ от такой попытки).
10. **RQ `staleTime: 30s` + `refetchOnWindowFocus: false`** глобально — главный DPI-выигрыш: список → деталь → назад стоит трёх TLS-соединений вместо одного; на мобильном Safari «focus» фаерится на каждом переключении приложения. Требует ручного QA (инвалидация, realtime-merge, 14 `refetchInterval`-поллеров).
11. Единый `getSession`-хук вместо трёх сетевых `getUser()` на холодном пути ученика (`usePractice`, `useDiagnostic`, `Chat.tsx`) — нарушение performance.md §2a.
12. `useNetworkStatus`: не вызывается `setStatus` в ветке `!online` (на Chrome/Android состояние залипает), probe бьёт в `google.com` вместо нашего бэкенда — то есть рапортует «Отлично» ровно в инцидент. Плюс убрать 30-секундный опрос.
13. CSS 214 КБ — **только если метрики покажут**; в один content-hashed файл, кэшируется навсегда, gzip даёт ~1/10.

### Этап 4 — КАЧЕСТВО КОДА

14. Vitest + тесты там, где ошибка = потерянные деньги или неверный балл ученика: ledger/баланс (append-only, credit↔debit симметрия), `computeFinalScore`, чекер Части 1 (оба зеркала), квоты 10/50.
15. `exhaustive-deps` в high-risk (`Chat.tsx`, `TutorSchedule.tsx`) — отдельной задачей с QA: наивное добавление зависимостей в этом репо исторически **создавало** баги (performance.md §2-bis).

## 3. Скиллы и внешние данные

- **Внешние данные применены сейчас:** пороги CWV и факт замены FID→INP взяты из актуальной документации (`web.dev/articles/vitals`), а не из памяти модели. Проверено также, что у Яндекс.Метрики нет документированного API-экспорта CWV — отсюда выбор своего пайплайна.
- **`optimize`** — скилл для этапа 3 (loading, rendering, bundle). Вызывать в момент работы над 9–13.
- **`audit`** — скилл для scored-отчёта P0–P3 (accessibility, performance, anti-patterns). Вызывать **после** этапа 1: аудит до деплоя измерит состояние, которое мы прямо сейчас меняем.
- **`preflight`** — перед каждым мержем (RU-bypass grep, typecheck, smoke-check, build).
- **rule 40 QA-чеклист конструктора** — обязателен, если этап 3 п.10 затронет `TutorHomeworkCreate`.
