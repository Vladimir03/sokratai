## 2. Анатомия наших запросов

### `chat_discussion` (обсуждение с Сократом) — самый дорогой по prompt

`supabase/functions/chat/index.ts`. Промпт собирается линейно:

```
SYSTEM_PROMPT (6923 симв ≈ 2.8–3.5k токенов, БАЙТ-В-БАЙТ одинаков у всех)
  → subject-блок с рубрикой ФИПИ/DELF
  → контекст задачи
  → эталон репетитора (anti-spoiler)
  → имя/пол ученика
  → предмет диалога, педагогический контекст
  → telegram-appendix
  → [история сообщений]
  → [картинки — в ПОСЛЕДНЕЕ сообщение пользователя, каждый ход]
```

Хорошая новость: **всё переменное дописывается в конец** — форма, идеальная для префиксного кэша. Внутри одного треда ДЗ system-промпт стабилен целиком (2.8k + рубрика + задача + эталон ≈ 4–5k токенов), меняется только хвост истории.

Плохая: `injectHomeworkImagesIntoLastUserMessage()` ([chat/index.ts:408](../../../../supabase/functions/chat/index.ts)) вешает **фото условия задачи в последнее сообщение на КАЖДОМ ходу**, то есть картинка (≈ 258–1120 токенов) всегда лежит в хвосте, куда префиксный кэш не достаёт принципиально.

⚠️ **Называть это «переплатой за каждый ход» — ошибка, и на ней легко принять неверное решение.** Массив сообщений целиком уезжает в каждом запросе при ЛЮБОМ размещении картинки: число отправленных токенов от переноса НЕ меняется. Меняется ровно одно — может ли картинка попасть в кэшируемый префикс. Значит выигрыш P1 **целиком производный от того, работает ли кэш**: не работает — перенос не даёт ничего, и делать его незачем.

### `homework_check` — 958 вызовов, самый частый

`homework-api/guided_ai.ts::buildCheckPrompt`. Отдельный вызов на каждую проверку ответа; средний промпт 2453 токена. Внутри одной задачи одного ученика проверок бывает 3–10 — и рубрика + условие + эталон уезжают целиком каждый раз.

### `kb_extract` — 495 вызовов, дороже всех по деньгам

`kb-ai-extract`. Единственный путь с `maxTokens: 16000`. Здесь оптимизировать нужно **выход**, а не вход: 1845 completion-токенов на вызов в среднем.

### Картинки — общий узел

Все пути инлайнят фото как base64: `createSignedUrl` → `fetch` → `btoa` ([_shared/ai-lovable.ts:287](../../../../supabase/functions/_shared/ai-lovable.ts)). Это обязательно — OpenAI-совместимый эндпоинт Gemini не ходит по внешним URL сам. Но:

- **ноль мемоизации**: та же тетрадь скачивается и кодируется заново на каждый вызов (латентность до старта AI, не токены);
- скачивания **последовательные** — 3 картинки = 3 round-trip'а внутри 35-секундного бюджета;
- клиент жмёт до 1600 px по длинной стороне; Gemini тайлит по 768 px, то есть 1600×1200 ≈ 6 тайлов.

## 3. Кэш: что бывает и что из этого доступно НАМ

### Implicit caching (автоматический)

Включён по умолчанию у Gemini 2.5+ без единой строки кода. Работает по **общему префиксу** с предыдущими запросами: совпал префикс — кэш-хит и скидка (по докам 75%, в свежих материалах — до 90% от цены input-токена). Минимум для срабатывания — 1024 токена (2.5 Flash) / 2048 (2.5 Pro); для `gemini-3-flash-preview` официального подтверждения порога нет.

Наш `SYSTEM_PROMPT` — 2.8k+ токенов, идентичен у ВСЕХ вызовов чата. Формально мы уже в условиях кэш-хита.

**Но проверить это мы не можем**, и вот почему это ключевой пункт: кэш — серверный, на стороне Google, ключ — проект Google **Lovable**, а не наш. Долетает ли скидка до нашего счёта в кредитах — неизвестно. Плюс `emitUsage()` читает только `prompt_tokens`/`completion_tokens`/`total_tokens` ([_shared/ai-lovable.ts:73](../../../../supabase/functions/_shared/ai-lovable.ts)) и **выбрасывает** `prompt_tokens_details.cached_tokens`, если шлюз его отдаёт.

### Explicit caching (`cachedContents` / `cached_content`)

Ты сам создаёшь объект кэша с TTL и ссылаешься на него. Через OpenAI-совместимый слой доступен как `extra_body.cached_content`. **Нам сейчас недоступен**: создавать cache-объекты может только владелец API-ключа, а ключ — Lovable. Появится, только если пойдём в Google напрямую (см. §5, «Развилка»).

### Кэш на нашей стороне

Единственный, который целиком в наших руках: мемоизация **инлайна картинок** (ref → data-URL). Токенов не экономит вообще — экономит секунды и трафик Storage.

## 4. План работ, по убыванию отношения «польза / риск»

### P0. Начать измерять кэш-хиты — 1 строка + 1 колонка ✅ СДЕЛАНО 2026-08-05 (`1984843`)

> Миграция применена, 6 функций задеплоены. Замер идёт со следующего AI-вызова; строки, записанные до деплоя, имеют `cached_tokens = NULL` не потому, что кэша нет, а потому что их писал старый код — при чтении отсекать по `created_at >= '2026-08-05 12:00+03'`.

В `emitUsage` вытащить `usage.prompt_tokens_details.cached_tokens` (и `cached_content_token_count`, шлюзы отдают по-разному), положить в `token_usage_logs.cached_tokens` (nullable int — миграция аддитивная).

Ценность непропорционально велика: **это единственный способ узнать, работает ли у нас implicit caching вообще**. Если через неделю там нули — вся ветка «префиксный кэш» закрыта, и мы не тратим на неё время. Если не нули — у нас появляется метрика, по которой видно эффект P1.

Риск: нулевой (fire-and-forget логирование, `emitUsage` уже обёрнут в try/catch).

### P1. Гигиена префикса: инвариантные картинки — в НАЧАЛО, не в хвост ❌ ОТМЕНЁН 2026-08-06

> Замер P0 дал `cached_tokens = 0` в 164 строках из 164 ⇒ выигрыш ровно нулевой при цене «правка критического пути грейдинга». Ниже — исходное описание, чтобы при появлении кэша не выводить его заново.

Условие задачи не меняется между ходами диалога — значит его место в первом сообщении, а не в последнем. Тогда оно (а) не переоплачивается каждый ход, (б) попадает в кэшируемый префикс, (в) перестаёт «прыгать» по позиции.

Решение ученика (меняется каждый ход) остаётся в хвосте — это правильно.

⚠️ Осторожно: rule 40 требует fail-closed на картинках (`student_images_missing`, image-only гейт `solution_text < 20`). Перекладывание картинок — правка КРИТИЧЕСКОГО пути грейдинга, только с прогоном QA-чеклиста конструктора и проверкой всех трёх AI-путей.

**Оценка выигрыша:** 258–1120 токенов картинки переезжают из полной цены в кэшированную (−75…−90% на них). **Без работающего кэша выигрыш РОВНО НОЛЬ** — см. предупреждение в §2. Поэтому P1 строго после P0, никогда параллельно.

### P2. Мемо-кэш инлайна картинок (латентность)

`Map<storage_ref, dataUrl>` на инстанс + дедуп внутри одного вызова. Даёт секунды на многокартиночных вызовах и снимает лишние round-trip'ы из 35-секундного бюджета. Инстансы edge эфемерны, так что кросс-вызовный эффект случайный — если захочется гарантий, нужна таблица с TTL, но это уже отдельная задача с уборкой мусора.

**Не даёт экономии токенов вообще.** Брать, только если целимся в латентность.

### P3. Бюджет контекста в токенах, а не в сообщениях

`chat_discussion` доходил до 14 645 токенов промпта. Сейчас история режется по числу сообщений (у чата репетитор↔ученик — 15). Правильнее — по бюджету символов/токенов: первый ход (контекст) + последние N, всё между — выкинуть или свернуть.

### P4. JSON-режим вместо «попроси JSON словами» — чинит 9 из 10 отказов ✅ СДЕЛАНО 2026-08-05

Все 4 копии вызова шлюза просят JSON текстом промпта. OpenAI-совместимый слой Gemini поддерживает `response_format: {"type":"json_schema"}` (и `json_object`) в обычном режиме. Это ровно тот класс отказов, который у нас в логах.

⚠️ Шлюз Lovable — посредник, и пробрасывает ли он `response_format`, документации нет.

**Как сделано (fail-open, без флага в конфиге).** `response_format: {type:"json_object"}` включён по умолчанию во всех трёх копиях вызова, которые парсят JSON (`_shared/ai-lovable.ts`, `homework-api/ai_shared.ts`, `mock-exam-grade`). Стриминговый `chat` не трогаем — там свободный текст.

Если шлюз ответит 400/422 — параметр выключается **на весь isolate** (`jsonModeDisabled`), пишется `<tag>_json_mode_unsupported`, и запрос немедленно повторяется без него. Три следствия, которые и делают правку безопасной:

- **проба не тратит бюджет ретраев** (`extraAttempts`): иначе у вызова с `fallbackModel` первый 400 ушёл бы на смену модели, второй — на отказ от json-режима, и попытки кончились бы ДО успешного запроса;
- **ложное срабатывание безвредно**: чужой 400 (например, по неизвестной модели) в худшем случае отключит режим — запрос всё равно уходит повторно. Проверка стоит ПОСЛЕ model-fallback, чтобы не перехватывать его случай;
- **цена неподдержки — один лишний запрос на холодный isolate**, а не на каждый вызов.

Отдельный готча: некоторые OpenAI-совместимые реализации требуют слова «JSON» в самих сообщениях при `json_object`, иначе 400. У нас промпты его содержат, но даже если где-то нет — сработает тот же фолбэк.

**Как проверить после деплоя:** `select error_code, count(*) from ai_gateway_errors where occurred_at >= '2026-08-05' group by 1` — `invalid_json` должен просесть. В логах функций искать `_json_mode_unsupported`: есть → шлюз параметр не принял (P4 не сработал, но ничего не сломал); нет и `invalid_json` падает → работает.

|---|---:|---:|---:|---|
| `guided_check` / `guided_hint` / физ-блок-схема | 704 | 209 | 4000 | ×5.7 |
| `_shared` (чат репетитора, эталон, kb-refine) | 959 | — | 4000 | ×4.2 |
| `kb_extract` | 12 224 | 9055 | 16 000 (было) | ×1.3 |
| `mock_grade` / `mock_ocr` | 487 / 2559 | — | 8000 | ×3.1 |
| `chat_discussion` (стриминг, текст) | 31 814 | 7353 | 10 000 | ×1.4 к p99 |

У пробников кап выше остальных намеренно: OCR бланка возвращает строку на задание, наблюдались 2559 при 20 заданиях, а у химии ЕГЭ их 28 (rule 45). У чата — 10 000, а не p99: путь стриминговый, обрезка видна ученику как оборванная фраза, поэтому режем патологию, а не длинный живой разбор.

### P6. OCR-once для фотоусловий (самый большой выигрыш и самый большой риск)

Колонка `ocr_text` уже есть. Идея: распознать условие один раз, дальше слать текст (~100–200 токенов) вместо картинки (258–1120) на всех последующих ходах и проверках.

Почему не первым пунктом: rule 40 прямо запрещает молчаливую деградацию картинок, а «[Задача на фото]» без фото — уже случавшийся у нас прод-инцидент. Нужна отдельная спека с правилом «когда картинка обязательна» (чертёж, график, рукопись → всегда картинка; печатный текст → OCR). Это продуктовое решение, не рефакторинг.

## 5. Развилка, которую стоит держать в голове

**Свой ключ Google вместо шлюза Lovable.** Даёт: explicit caching, Batch API (−50% для не-срочных путей вроде `kb_extract`), выбор модели под задачу, честную телеметрию кэша. Стоит: отдельный биллинг, ключи, и потеря бесплатных/льготных кредитов Lovable. По памяти проекта AI-вызовы уже идут не с RU-IP, так что блокировки тут не аргумент.

**Сейчас это не окупается** ($7/мес). Пересматривать при ×10 нагрузки или если P0 покажет, что скидка за кэш до нас не доходит.

> **ЗАКРЫТО 06.08.2026 — см. «Развязку» вверху.** Обе половины условия проверены и обе против ухода: скидка за кэш до нас действительно не доходит (`cached_tokens` = 0 в 164 строках из 164), **но и наценки у шлюза нет — она ≈1,00×**, то есть Lovable отдаёт прайс Google один в один. Уход даёт не экономию, а лишний биллинг: OpenRouter на том же объёме = $8,31 против $7,92 у Lovable (комиссия пополнения 5,5%), и оплата российской картой там не проходит. Возвращаться к развилке имеет смысл только ради **Batch API** (−50% на `kb_extract`, который даёт 78% счёта AI) — и это отдельная задача про асинхронность загрузчика, а не про смену шлюза.

## 6. Что НЕ делать

- **Не кэшировать ОТВЕТЫ AI между учениками.** Один и тот же вопрос от другого ученика — другой тред, другая история, другой эталон; плюс это прямой путь протащить чужой `solution_text` мимо anti-leak (rule 40). Экономия копеечная, риск — категория «утечка».
- **Не тащить explicit caching через шлюз наугад.** Без своего ключа объект кэша не создать; попытка «а вдруг пробросит» даст тихое игнорирование параметра, и мы будем считать, что оптимизировали.
- **Не резать разрешение картинок «на глаз».** 1600 px по длинной стороне выбраны под рукописные решения; экономия тайлов обернётся нераспознанным почерком — то есть неверной оценкой ученика.
- **Не оптимизировать `chat_discussion` по длине системного промпта.** Он длинный осознанно (методология, рубрики, анти-спойлер), и он же — главный кандидат в кэшируемый префикс. Резать его = уменьшить кэш-хит и ухудшить качество ради $1.

## 7. Порядок, если браться

Разделение простое: **от замера зависит ТОЛЬКО P1.** Остальное не про кэш, и держать его в заложниках у недели наблюдений незачем.

1. **P0** (измерение) — ✅ сделано 05.08. Неделя данных.
2. **P4 + P5** (`response_format`, `max_tokens`) — ✅ сделано 05.08 (`2409b6e`…). Ждать замера было не нужно: это надёжность и потолок расходов, а не кэш.
3. **P1** (префикс-гигиена) — **строго после** P0 и только если `cached_tokens > 0`. При нулях выигрыш ровно нулевой, а цена — правка критического пути грейдинга.
4. **P2/P3** — когда займёмся латентностью guided-чата (отдельный триггер: жалобы на «долго думает», а не счёт).
5. **P6** (OCR-once) — отдельной спекой, не в рамках этой задачи.

**Как читать данные через неделю:**

```sql
select source, count(*) n, count(cached_tokens) reported,
       sum(cached_tokens) cached, sum(prompt_tokens) prompt
from token_usage_logs
where created_at >= '2026-08-05 12:00+03'
group by source order by prompt desc;
```

`reported = 0` при ненулевом `n` → шлюз кэш-метрику не отдаёт вовсе: ветка префиксного кэша закрыта (P1 не делаем), остаются P4/P5 и развилка из §5. `cached > 0` → кэш живой, P1 обоснован, и по доле `cached/prompt` видно потолок выигрыша.
